## 2. Теоретическая оценка и прогноз ДО запуска

SRAM содержит статические данные (глобальные/static-переменные и буферы), кучу (динамическая память) и стек (адреса возврата, локальные переменные, сохранённые регистры и часть аргументов). Стек обычно растёт навстречу свободной памяти и куче. Когда памяти не хватает, повреждаться могут данные программы.

В deepRecursion() есть локальный массив из 16 байт. Однако **кадр больше массива**, потому что нужны также служебные данные вызова. Без файлов компилятора .su для предварительного расчёта **предположим 24–32 байта на кадр**. Дополнительно условно закладываем 300 байт статических данных/служебных буферов, 150 байт исходного стека и 200 байт резерва. Это допущения, не измерения.

**Формула:** N ≈ (2048 − статические данные − исходный стек − резерв) / размер кадра.

Подставляем: 2048 − 300 − 150 − 200 = **1398 байт**. При 24 байтах/кадр N ≈ 58; при 32 байтах/кадр N ≈ 44; при 28 байтах/кадр N ≈ 50.

**Прогноз для рекурсии:** риск нехватки SRAM примерно на глубине 44–58. Возможны зависание, прекращение/искажение Serial-вывода, перезапуск или другой симптом. Конкретный симптом не гарантирован.

**Прогноз для итерации:** цикл до 10000 напечатает 0, 1000, …, 10000 и SAFE FINISH. Расход стека будет **приблизительно постоянным**, но не нулевым.

**Прогноз для Memory Hog:** каждый одновременно активный вызов содержит volatile int buffer[300], на AVR int занимает 2 байта, значит только массив использует примерно 600 байт. Для начального level 0, 1, 2, 3, 4 — соответственно 1, 2, 3, 4, 5 одновременных кадров, то есть 600, 1200, 1800, 2400, 3000 байт только на массивы. Уровень 2 уже рискован с учётом накладных расходов; уровни 3–4 превышают 2048 байт одними массивами.

## 3. Рекурсивный эксперимент

**Код:** [code/crash.ino](code/crash.ino).

Функция без базового случая увеличивает глубину на 1. Атрибут noinline запрещает встраивание. volatile требует реальных обращений к локальному массиву. Операция после рекурсивного вызова не позволяет заменить её оптимизацией хвостовой рекурсии. Serial выводит значение только на каждом 10-м уровне, чтобы уменьшить влияние диагностики.

- Прогноз: риск около 44–58, возможны различные симптомы переполнения.
- Последняя корректная напечатанная глубина: **10**.
- Наблюдаемый симптом: после `START` и `10` последовательность вывода прекратилась. На присланном скриншоте симуляция работала около **24.176 с**, нового `START` и видимого перезапуска не было. Это свидетельствует о нарушении нормального выполнения/вывода, но **не позволяет определить точный уровень повреждения памяти**.
- Скриншот Crash: получен в переписке 13.11.2026; **ожидает сохранения в GitHub как** `screenshots/crash_result.png`. На изображении видны код, плата Arduino Uno, Serial Monitor (`START`, `10`) и длительность ~24 с.
- Расхождение: прогнозируемый риск 44–58 вызовов, но **последнее напечатанное значение — 10**. Это не доказывает, что сбой произошёл точно на глубине 10, потому что печать выполняется каждые десять уровней. Причины расхождения:
  1. Предположения о размере кадра, статических данных и резерве могут отличаться от реальной компиляции и использования SRAM.
  2. Serial и библиотечные функции тоже расходуют память, а печать лишь каждые 10 уровней скрывает точную глубину сбоя.
  3. Переполнение стека имеет неопределённое поведение: повреждение памяти не обязано немедленно вызвать перезагрузку.

## 6. Инженерный вывод

У Arduino Uno всего 2 КБ SRAM, и неконтролируемая рекурсия может исчерпать доступное пространство для стека. При переполнении возможны зависание, перезапуск или незаметная порча данных, поэтому нельзя рассчитывать только на один ожидаемый симптом. Отсутствие перезапуска не доказывает, что программа работала корректно. Итерационный алгоритм с ограниченным числом повторений не создаёт всё более длинную цепочку одновременно активных вызовов, поэтому его расход стека остаётся приблизительно постоянным. Опыт Memory Hog демонстрирует, что память локальных массивов суммируется, пока вызовы вложены друг в друга. В реальных встроенных системах необходимо заранее оценивать пиковую SRAM и оставлять резерв для библиотек и прерываний. Особенно важно ограничивать глубину вызовов и предусматривать безопасное восстановление после отказа.
